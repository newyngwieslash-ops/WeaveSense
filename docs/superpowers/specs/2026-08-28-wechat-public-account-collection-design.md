# 第三方微信公众号定时采集设计

日期：2026-08-28  
状态：用户已批准，进入实施计划  
适用项目：织识 Loom

## 1. 目标

为 100 个以上、无管理权限的第三方公开微信公众号建立持续采集能力：

- 标题、发布时间、公众号名称和原文链接为必须字段。
- 正文与封面图尽力采集；失败不能阻塞必须字段入库。
- 正常情况下 95% 的新文章在发布后 2 小时内发现。
- 每日付费数据对账补齐已被付费供应商收录、但自建来源漏掉的文章。
- 连续 24 小时无法成功检查的公众号必须进入可见告警。
- 自建来源承担日常流量，极致了数据 API 作为首版付费兜底。

首阶段在当前项目验证；验证通过后迁移到具备固定公网出口、可长期运行 Docker 的服务器。

## 2. 非目标

- 不接入微信公众号管理后台，也不要求目标公众号的 AppID、AppSecret 或管理员权限。
- 不在主应用中模拟微信登录、保存微信 Cookie 或实现验证码绕过。
- 不承诺获取非公开、已删除、需要额外权限或上游未收录的内容。
- 首版不建设多个付费供应商的通用插件框架。
- 首版不采集阅读数、点赞数、评论和粉丝数据。
- 不因上游删除或暂时不可用而删除已经入库的文章。

## 3. 已有能力与复用范围

项目已经具备：

- `wechat` 平台与 RSS/WeWe/RSSHub 信源入口。
- 按信源配置的扫描周期、增量游标、任务日志和错误状态。
- RSS/Atom 解析、文章归一化、数据库持久化与内容展示。
- `(source_id, external_id)` 唯一约束及关键词、分析、媒体处理管道。

本设计复用这些能力。主应用不新增公众号页面抓取器；新增能力集中在源网关、稳定去重、服务器定时触发、批量导入和健康状态展示。
微信公众号正文保存为清洗后的完整纯文本；现有 8,000 字符截断对该适配器取消，改为单篇 2 MB 的输入上限。超过上限时记录错误并只保存必须字段，不截出一个看似完整的正文。

## 4. 方案选择

采用“独立源网关 + 付费 API 兜底”：

```text
公众号清单
    ↓
自建公众号源网关（主来源：每个账号的 WeWe/RSSHub 兼容 Feed）
    ↓ 技术失败、长时间未成功或每日对账
极致了数据 API
    ↓
现有 Loom 调度器与采集管道
    ↓
PostgreSQL / PGLite、内容列表、任务日志、告警
```

源网关与主应用分离，因为微信登录状态、上游风控和供应商密钥不属于 Web 控制面。源网关只向主应用暴露统一、受保护的 Atom Feed 和健康状态接口。

## 5. 组件边界

### 5.1 公众号源网关

新增长期运行的 Docker 服务 `wechat-gateway`，职责是：

- 保存每个公众号的稳定标识、样例文章链接、主 Feed 地址和健康状态。
- 优先读取自建的 WeWe/RSSHub 兼容 Feed。
- 将不同来源归一化为统一文章结构。
- 根据确定的状态机调用极致了数据 API。
- 暴露 `GET /v1/feeds/{source_id}.atom` 与 `GET /v1/sources/{source_id}/health` 两个内部接口。
- 缓存上游响应，避免多个主应用请求重复消耗付费额度。
- 在持久卷中的 SQLite 数据库保存提供商状态；主应用数据库不是网关状态的第二份真相。

网关不负责内容展示、知识分析或业务搜索。

### 5.2 Loom 主应用

主应用继续负责：

- 管理公众号信源及扫描周期。
- 每小时扫描到期信源。
- 去重、入库、任务记录、内容展示和后续正文处理。
- CSV 批量导入与健康状态页面。

### 5.3 定时触发器

新增服务器内部定时入口，并由 Docker 中的轻量定时进程每小时调用。入口必须验证服务器环境变量中的 `CRON_SECRET`；不得暴露无鉴权的付费采集触发能力。

浏览器页面可继续提供手动扫描，但页面定时器不再承担生产调度职责。

## 6. 统一文章结构与传输

网关内部使用以下逻辑结构：

```ts
type WechatGatewayItem = {
  account_id: string;
  account_name: string;
  title: string;
  published_at: string;
  original_url: string;
  canonical_id: string;
  body_html?: string;
  body_text?: string;
  cover_url?: string;
  provider: "primary" | "dajiala";
  discovered_at: string;
};
```

对主应用输出 Atom 1.0：`id` 对应 `canonical_id`，`title` 对应标题，`published` 对应发布时间，`link rel="alternate"` 对应原文链接，`author` 对应公众号名称，`content` 对应正文，`media:thumbnail` 对应封面，`loom:provider` 与 `loom:discovered_at` 保存来源元数据。主应用的微信网关适配器复用现有 RSS 解析器，只增加这两个扩展字段和服务器端鉴权头。

缺少标题、合法发布时间或微信原文链接的记录不得作为正常文章入库，应记录为供应商数据错误。发布时间统一转换为带时区的 ISO 8601；无时区的微信时间按 Asia/Shanghai 解释。正文和封面为空是允许状态。

## 7. 去重规则

按以下优先级生成 `canonical_id`：

1. 从原文链接解析 `__biz + mid + idx`。
2. 使用移除追踪参数、临时签名和锚点后的规范化微信原文链接。
3. 使用 `account_id + 标准化标题 + 发布日期` 生成指纹。

数据库继续保留现有唯一约束，同时把 `canonical_id` 写入 `external_id`。同一文章由主来源和极致了重复返回时只保留一条，并在 `extra.providers_seen` 中累计来源。

## 8. 调度与故障切换

### 8.1 常规扫描

- 每小时扫描一次到期公众号。
- 单个公众号的主 Feed 成功返回，即使没有新文章，也记为“成功无更新”。
- 只有网络错误、鉴权错误、解析错误、限流或明显无效响应才计为技术失败。

### 8.2 付费兜底触发

满足任一条件时调用极致了数据：

- 主来源连续两次技术失败。
- 主来源连续 6 小时没有一次成功检查。
- 每日对账发现该公众号当天尚未完成供应商核验。

首版使用极致了“当天发文情况”或“历史发文列表”接口发现缺失文章。正文与封面只在主来源未提供、且文章已确定缺失时调用文章详情或 HTML 正文接口。

### 8.3 每日对账

- 每天 23:30（Asia/Shanghai）对全部启用公众号进行一次元数据对账，以覆盖晚间发布并尽量满足当天补齐目标。
- 对账只比较标题、发布时间、账号和原文链接。
- 当天新增缺失文章立即补入库；正文和封面进入异步尽力提取。
- 当天已成功调用过付费 API 的公众号不重复调用，除非前次结果为技术失败。

### 8.4 调用预算

- 首版默认同时限制为每天 250 次且不超过 20 元，任一上限先到即停止；通过服务器环境变量调整。
- 达到 80% 预算时生成预警。
- 接近上限时优先处理最久未成功检查、当日有发布迹象或高优先级的公众号。
- 达到上限后停止新的付费调用，但继续自建来源扫描并生成明确告警。
- API Key 只存放在源网关的服务器环境变量中。

## 9. 状态与数据存储

网关持久化数据库新增一张按公众号保存的提供商状态表，字段包含：

- `source_id`
- `account_id`
- `primary_feed_url`
- `last_primary_ok_at`
- `consecutive_primary_failures`
- `last_paid_check_at`
- `last_paid_result`
- `next_retry_at`
- `alert_state`

主应用任务记录增加实际提供商、尝试顺序和付费调用标记。文章的来源历史、规范化链接和正文/封面提取结果保存在现有 `extra` 与媒体字段中，不另建重复内容表。健康页面实时读取网关健康接口，不复制网关状态表。

不得将微信 Cookie、扫码会话、付费 API Key 或内部定时密钥写入当前无账号数据库。

## 10. 批量接入

信源页增加 CSV 导入，列为：

```text
name,wechat_id,sample_url,primary_feed_url,interval_minutes,priority
```

规则：

- `name`、`sample_url` 和 `primary_feed_url` 必填。
- `interval_minutes` 首版统一接受 `60`；其他值拒绝并提示。
- `priority` 只允许 `normal` 或 `high`，默认 `normal`。
- 导入前预览有效、重复和错误行；确认后只写入有效且不重复的记录。
- 单次支持至少 500 行。
- 导入时先在网关创建或校验账号映射；网关成功后再写入主应用信源，避免只创建一半。

## 11. 健康与告警

信源页或节点页展示：

- 最近一次主来源成功时间。
- 连续失败次数与最近错误类型。
- 最近一次付费核验时间和结果。
- 当天付费调用次数。
- 当前状态：正常、降级、付费兜底、告警。

连续 24 小时没有任何成功检查时进入告警；恢复成功后自动解除，但保留任务历史。

## 12. 极致了数据首版接入

选择理由：

- 提供按公众号查询当天发文与历史发文列表的接口。
- 提供文章详情和 HTML 正文接口。
- 支持按调用计费，适合只在失败和每日对账时使用。
- 公开资费便于在验证阶段限制成本。

验证前先使用试用额度抽测 20 个公众号，连续三天检查：

- 指定账号能否稳定定位。
- 标题、发布时间和链接是否准确。
- 返回的短链接能否稳定解析、去重和访问。
- 当天发文接口的发现延迟。
- 正文及封面字段的实际覆盖率。

若必须字段有效率低于 99%，或当日已发布文章在每日对账后仍持续缺失，则停止首版采购并改用清博微信 API 试用。清博公开资料显示其更新周期约 24 小时，因此只作为每日对账替代，不承担两小时发现目标。

## 13. 错误处理

- 网络、5xx 与限流采用有上限的指数退避。
- 单轮重试等待为 5、15、60 分钟，第三次仍失败后等待下一小时调度。
- 4xx 参数错误直接失败并要求修正账号映射，不重复消耗额度。
- 主 Feed 返回空列表不自动视为失败；只有结构无效或健康检查失败才触发降级。
- 供应商返回重复、缺字段或异常时间时记录原始摘要和错误类型，不写入坏数据。
- 已入库文章不因上游删除、Feed 缩短或供应商结果变化而删除。
- 任一单源失败不得阻塞其他公众号扫描。

## 14. 验证与测试

### 14.1 自动检查

- `canonical_id` 对长链接、短链接、追踪参数和缺失参数的单元测试。
- 主来源成功、连续失败、6 小时降级、每日对账、预算耗尽和恢复的状态机测试。
- CSV 导入的有效行、重复行、错误行和 500 行批量测试。
- 相同文章由两个提供商返回时只入库一次的集成测试。
- 定时入口无密钥、错误密钥和正确密钥的鉴权测试。

### 14.2 分阶段实测

1. 10–20 个不同发文频率和文章形式的公众号，连续运行 72 小时。
2. 扩至 100 个以上，验证并发、限流、成本上限和每日对账。
3. 在长期 Docker 服务器连续运行一周，验证重启恢复、持久化和固定出口。

### 14.3 验收指标

- 必须字段有效率不低于 99%。
- 以人工核对和极致了试用结果的并集作为参考集，至少 95% 的参考文章在发布后 2 小时内发现。
- 每日对账后，极致了已收录的缺失文章全部补齐。
- 重复入库率低于 0.1%。
- 正文提取率目标不低于 80%，封面提取率目标不低于 90%。
- 连续 24 小时未成功检查的公众号全部出现在告警列表。
- 付费调用不得突破配置的每日上限。

## 15. 部署与迁移

验证阶段可在当前环境手动或短期运行网关和定时触发器；不把页面保持打开视为生产调度。

生产阶段使用 Docker Compose 长期运行：

- Loom 应用
- PostgreSQL
- 公众号源网关
- 自建 WeWe/RSSHub 兼容 Feed 服务
- 定时触发器
- 现有媒体存储与其他工作节点

数据库和网关状态使用持久卷。服务器必须具备固定公网出口；所有密钥通过运行环境注入，不写入镜像、仓库或数据库。

## 16. 实施顺序

1. 建立稳定 ID 与去重测试。
2. 增加提供商状态表和状态机。
3. 建立源网关及主 Feed 接口。
4. 对接极致了试用 API。
5. 增加受保护的服务器定时触发。
6. 增加 CSV 批量导入和健康状态展示。
7. 完成 20 个账号的 72 小时验证。
8. 扩展到 100 个以上并执行一周 Docker 验证。

只有验证指标通过后，才进入长期服务器采购和正式规模化运行。
