## 1. 方法（真实管线，仅桩掉网络）

| 项目 | 做法 |
|---|---|
| 调度路径 | **真实** `tickDueSources`（含并发池、租约、预算、去重、游标推进） |
| 数据库 | **真实** PostgreSQL 16 容器（每次运行新建，运行后删除）；20 项迁移全量应用 |
| 采集入口 | 真实 RSS 解析器与入库/合并路径 |
| 网络 | **仅**替换 transport（T06 引入的注入缝），feed 由进程内生成；**零外网** |
| 轮次 | 每源：第 1 轮 10 条 → 第 2 轮再 10 条（**共 20 条**）→ 第 3 轮重放第 2 轮内容（期望新增 0） |

| 关键词 | 每轮 2 个关键词；搜索端点返回空的有效响应（非本评测对象） |

### 关于计划中的延迟门槛（P95 due-to-start ≤ 120 秒）

计划建议"候选小规模 P95 due-to-start ≤ 120 秒"。本次测量中：

- **1000 源单轮全部到期工作完成耗时 3.9—4.1 秒**，单 tick（200 源上限）约 **130 ms**。
- 因此在我们能测到的范围内，**due-to-start 远低于 120 秒**（最多约 4 秒）。
- **但这不是那个门槛的证据**：计划的门槛针对**真实的 5/10 分钟调度节奏与真实网络时延**，而这里是本地桩、每轮一次性排空。**T09 建议的 P95≤120 秒仍标记为未验证**，需 T23 的真实持续运行来测。

## 3. 慢源与饥饿

桩传输让每第 97 次调用慢 120 ms（确定性少数）。结果：1000 源时 3030 次调用中包含约 31 次慢调用，**错误 0、deferred 0、每源条数均匀为 20**——没有快源被慢源饿死的迹象（并发池 `CRON_SOURCE_CONCURRENCY=9` 生效）。

## 4. 确定性

`--seed 20260916` 固定语料与源命名；两次运行的同规模结果一致（1000 源：第 1 轮 4085 ms / 第 2 轮 3915 ms，条数与错误数完全相同）。

## 5. 明确的边界（不得越界解读）

- **这是突发测量**：单轮一次性排空，**不是** 72 小时 / 7 天持续运行（T23 范围）。
- **不构成真实平台容量声明**：真实 RSS/平台有网络时延、限流、失败重试、真实内容大小差异；本评测**零外网**。
- **不覆盖**：媒体落盘（MinIO）、OCR/ASR、模型调用、微信网关付费路径、对账窗口。
- **不覆盖**：内存峰值（未采集；本地 Node 进程未做堆采样）。
- 因此：**不得据此宣称"1000 信源可稳定运行"**。范围表（release-scope）中的规模承诺仍为 pending，直到 T23 给出真实证据。

## 7. 过程中发现并修正的评测脚本缺陷（保留追溯）

1. `pg.Client.query` 返回结果对象，初版按数组解构 → `(intermediate value) is not iterable`。
2. 注入缝传错参数位：`tickDueSources(limit, budget, io)`，初版传成第二参数被当作 budget，导致 transport 调用为 0、全部源报错。
3. 未设置 `DATABASE_URL`，调度器落回进程内 PGLite，导致"采集成功但库里为 0 行"。
4. 桩传输用调用计数当**源索引**，使每次请求看似不同源 → 重放也会新增、每源条数超过 20。改为从请求 URL 解析索引后，重放新增 0、每源恰好 20。
5. 第 2 轮最初未推进轮次、后又未回拨 due 时间 → 首版第 2 轮 0 源。均已修正为受控轮次推进 + due 回拨。
6. 搜索端点收到 RSS 体导致 B 站 JSON 解析失败（`invalid_response`，**T08 的正确行为**），在本评测中属噪声，已改为按端点返回空的有效响应。

以上每次失败尝试的原始输出均保留在对应 `logs/t17-*.txt`（含修正前的 `ok:false` 记录与"保留容器"提示）。
